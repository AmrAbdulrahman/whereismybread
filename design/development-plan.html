Where's My Money · Engineering

Build plan: a personal money-planning app

A feasible, sequenced path from empty repo to a polished 1.0 — Nx workspace, Next.js App Router, self-owned authentication, Supabase Postgres, and a one-click "get the latest build" flow. Seven build phases, each with a concrete exit criterion.

01 Decisions locked

Three questions were settled before planning; the rest are sensible defaults that can be revisited but shouldn't block the start.

Confirmed choices

Authentication
Auth.js (NextAuth v5), Credentials provider. We own the users table, password hashing, and the reset-token flow — no third-party identity provider.
Data layer
Drizzle ORM against Supabase Postgres. Schema and migrations live in an Nx lib; queries are fully typed. supabase-js is not used — Auth.js owns sessions.
UI
Tailwind CSS + Radix primitives, shadcn-style: components are copied into a shared UI lib and fully owned, matching the bespoke "Command Deck" dark design.

Defaults adopted

Package manager
pnpm (Nx + Vercel first-class).
Transactional email
Resend, with React Email templates (verification + password reset).
Client data cache
TanStack Query over Server Actions; optimistic updates for ticks and edits.
Validation
Zod at every trust boundary (server actions, env, API routes).
Testing
Vitest + Testing Library (unit/component), Playwright (e2e), axe (a11y).
Observability
Sentry (@sentry/nextjs) + Vercel Analytics.
Rate limiting
Vercel KV (Upstash) sliding-window on auth endpoints.

02 Workspace architecture

One thin Next.js app. Every business feature is its own standalone Nx library named feature-<name> — there is no umbrella "feature" project. Shared concerns are separate libs too. Import rules are enforced by lint, not convention.

Directory layout

# pnpm + Nx integrated monorepo — every lib below is its own Nx project
apps/
  web/                       Next.js App Router app — routing, layouts, page composition only
  web-e2e/                   Playwright suite

libs/
  feature-payments/          upcoming payments, list + calendar + year views, create/edit
  feature-subscriptions/     recurring payments + renewal date
  feature-installments/      fixed-amount plans, schedule computation
  feature-checklist/         monthly manual-transfer to-do list
  feature-debts/             debts + partial/full settlements
  feature-payment-methods/   methods + customisable icon & colour
  feature-tags/              tag management

  auth/                      Auth.js config, session helpers, password + reset-token logic, guards
  db/                        Drizzle schema, migrations, client factory, seed, repository base

  ui/                        design system: Radix + Tailwind primitives, tokens, AppShell, icon registry
  domain/                    cross-domain types + Zod schemas + money/recurrence/date utilities
  config/                    Zod-validated env (server + client), constants
  updates/                   build-version check hook + UI
  testing/                   factories, render helpers, DB harness

Each feature-<name> is a full Nx project: its own project.json, its own lint / test / build targets, its own tsconfig path alias (@wmm/feature-payments…), and its own tags. Adding a feature is nx g @nx/react:lib feature-<name>, never a folder inside an existing lib.

Library taxonomy & boundaries

Each lib is tagged; @nx/enforce-module-boundaries rejects imports that cross a boundary the wrong way. The feature-* libs never import each other — they compose only in apps/web.

Lib tags May depend on
apps/web type:app any lib
feature-payments, feature-debts, … (7) type:feature, scope:<domain> type:data, type:ui, type:util, type:auth — never another type:feature
auth type:auth type:data, type:util, type:config
db type:data type:util, type:config
ui type:ui type:util only
domain, updates, testing type:util type:util, type:config
config type:config nothing

Each feature-<name> starts as a single project with an index.ts barrel. Split one into feature-<name> + data-access-<name> + ui-<name> only once it visibly outgrows that — premature fragmentation costs more DX than it saves.

App Router structure

apps/web/src/app/
  (auth)/
    login/  signup/  forgot-password/  reset-password/[token]/
  (app)/
    layout.tsx            // AppShell + server-side auth guard
    page.tsx             // redirect → /calendar
    calendar/            // list | calendar | year toggle
    subscriptions/  installments/  checklist/  debts/
    tags/  methods/  settings/
  api/
    auth/[...nextauth]/route.ts
    version/route.ts     // deploy identity, no-store
    blob/upload/route.ts // signed client-upload handler
  layout.tsx   globals.css

Route groups keep the authenticated shell ((app)) and the public auth screens ((auth)) on separate layouts. Middleware guards the (app) group; server components read the session through libs/auth’s getCurrentUser().

04 Data model

All tables carry user_id, created_at, updated_at. Money is stored as integer minor units plus an ISO currency code — never floats. Due dates are date; audit stamps are timestamptz. Recurrence math runs in users.timezone.

Identity & auth

Table Purpose & notable columns
users email (unique, citext), password_hash, email_verified_at, name, timezone, default_currency.
password_reset_tokens user_id, token_hash (SHA-256 of a 32-byte secret), expires_at (30 min), used_at. Single-use.
email_verification_tokens Same shape; 24 h TTL.
auth_attempts Optional. identifier, kind, ip, created_at — backs lockout + audit if KV is unavailable.

No sessions or accounts table — JWT sessions are stateless and there is no OAuth linkage.

Money movements

Table Purpose & notable columns
tags name, color. Unique per (user_id, name).
payment_methods name, kind enum direct_debit | credit_card | cash | manual_transfer, icon_key, color, reference.
payments name, amount_minor, currency, method_id, recurrence enum one_time | monthly | quarterly | annual, anchor_date, day_of_month, ends_on, notes.
payment_tags Join: (payment_id, tag_id).
payment_events Actuals only. payment_id, due_date, status enum scheduled | paid | skipped, paid_at, amount_minor. Upcoming occurrences are computed on read, not materialised.

Subscriptions & installments

Table Purpose & notable columns
subscription_details 1:1 with payments. renewal_date, started_on, reminder_days_before. A subscription is a recurring payment with this row attached.
installment_plans name, installment_minor, frequency enum monthly | quarterly, day_of_month, basis enum end_date | total_amount, ends_on, total_minor, start_date, method_id. The unused bound is null; the other is derived.
installment_payments plan_id, sequence_no, due_date, status, paid_at, amount_minor. Generated from the plan; regenerated on edit while preserving paid rows.

Checklist & debts

Table Purpose & notable columns
manual_transfer_checklists month (first-of-month date), created_at, regenerated_at. Unique per (user_id, month).
manual_transfer_items checklist_id, source_payment_id (nullable), name, amount_minor, due_date, status enum open | done, done_at, sort_order. A snapshot — editable without touching the schedule.
debts counterparty, reason, direction enum i_owe | owed_to_me, original_minor, opened_on, status enum open | settled, settled_on.
debt_settlements debt_id, amount_minor, settled_on, method_id, kind enum partial | final, note. Remaining balance = original − Σ settlements.

The year heatmap and monthly totals are derived at query time from payment_events, installment_payments, and scheduled occurrences — no dedicated table.

Ownership & access

All DB access is server-side through a repository layer in libs/db; every function takes userId and scopes its query. Row-Level Security is added as defense-in-depth in Phase 2 — a per-transaction SET LOCAL app.user_id plus USING (user_id = current_setting('app.user_id')::uuid) policies — so a missing WHERE clause fails closed rather than leaking.

05 Authentication

Self-owned email + password. Auth.js handles the session cookie, CSRF, and callback plumbing; everything user-facing is ours.

Flows

  • Sign up — Zod-validated server action → check breached-password (HIBP k-anonymity range API) → argon2id hash → create users row → send verification email. Login is allowed immediately; unverified accounts are gated out of email-bearing actions (reminders).
  • Log in — Credentials authorize() looks up the user, verifies the hash, returns the session subject. Rate-limited per IP + email (sliding window, KV). Generic "Email or password is incorrect" on every failure.
  • Forgot password — always responds 200 ("If that email exists, a link is on its way"). If the account exists, mint a 32-byte token, store only its SHA-256, email the link. Request endpoint is rate-limited.
  • Reset password — validate token hash + expires_at + used_at is null → set new hash → mark token used → bump a password_changed_at claim so existing JWTs stop validating.
  • Account — change password (re-enter current), change email (re-verify), sign out.

Hardening checklist

  • Email enumeration closed on signup and forgot-password (uniform responses + timing).
  • Token entropy ≥ 256 bits; tokens stored hashed; single-use; short TTL.
  • AUTH_SECRET rotated capability; __Secure- / __Host- cookies, SameSite=Lax, Secure in prod.
  • Argon2id params tuned to ~100 ms on the deploy runtime.
  • Login + reset-request rate limits; progressive lockout on repeated failures.
  • Auth.js pinned to an exact version and fully wrapped by libs/auth so a breaking upgrade is a one-file change.

libs/config parses these through Zod at module load; a missing or malformed variable fails the build, not a request.

Database connection

Runtime uses the pooled URL with postgres(url, { prepare: false }) — the transaction-mode pooler cannot hold prepared statements, and forgetting this flag produces intermittent prepared statement "s0" already exists errors under load. Migrations use the direct URL.

Migrations

drizzle-kit generate in development; drizzle-kit migrate runs as an explicit CI job on merge to main, against POSTGRES_URL_NON_POOLING, behind a Postgres advisory lock, before the Vercel production alias is promoted. Never in next build — build runs on every preview and in parallel.

CI/CD

  • GitHub Actions: nx affected -t lint test build with nx-set-shas + Nx Cloud distributed cache.
  • Vercel preview deploy per PR; Playwright e2e runs against the preview URL.
  • Merge to main → migrate job → Vercel production promote.
  • Preview data: a shared Supabase dev project (or Supabase branching), seeded by libs/db’s seed script.

File storage

Vercel Blob, wired in Phase 0 and first used in Phase 6. Uploads go through a signed handleUpload route so files bypass the Server Action body limit; the returned URL is stored on the owning row (users.avatar_url, payment_events.receipt_url, debt_settlements.receipt_url).

07 Update mechanism

Goal: a user can pull the newest deployment on demand and never operate a stale bundle — an explicit "Check for updates" action, plus a quiet nudge when a new build lands mid-session.

  1. Stamp the bundle. The build injects NEXT_PUBLIC_BUILD_ID (commit SHA, falling back to deployment ID). It travels inside the JS, so the running client always knows which build it is.
  2. Report the live version. GET /api/version returns { buildId, commit, builtAt } with Cache-Control: no-store. It executes on whichever deployment is currently live, so its answer is by definition the latest.
  3. Compare. libs/updates exposes useUpdateCheck(), which fetches /api/version (cache: 'no-store') on: the manual trigger, visibilitychange → visible, a 15-minute interval, and each client navigation. A mismatch against NEXT_PUBLIC_BUILD_ID sets updateAvailable.
  4. Surface it. A Check for updates item in the app menu (spinner → "You're on the latest version" or "Update available"), plus a non-blocking toast when the passive check flips the flag.
  5. Apply. On confirm, window.location.reload(). Vercel revalidates the document and asset manifest, so the reload boots the new hashed bundles. Users who don't reload keep working — prior deployments' assets stay addressable.
  6. Bridge the gap. Vercel Skew Protection is enabled, so requests from a not-yet-reloaded client are pinned by x-deployment-id to a backend that still matches their code.

No service worker in 1.0: immutable hashed assets plus HTML revalidation make a plain reload sufficient. A service worker is only worth adding if offline support is later scoped — and then it must skipWaiting() and drive the same updateAvailable signal.

08 Mobile-first

The design baseline is a 375 px phone; everything is built there first and enhanced upward. Tailwind's mobile-first breakpoints, plus container queries on lib components so a card is correct regardless of the column it lands in.

Surface < md (phone) ≥ lg (desktop)
Navigation bottom tab bar (Calendar, Subscriptions, Installments, Checklist, Debts) + "More" sheet persistent left sidebar
Calendar agenda list (the List view) is the default month grid + day detail panel
Methods / Debts / Installments stacked cards row layout with inline detail
Create / edit forms bottom sheet side panel or inline
Year heatmap horizontal-scroll container with month ticks full 53-week grid
  • 100dvh and env(safe-area-inset-*); real inputs only — no painted status bar or keyboard.
  • Hit targets ≥ 44 px; the design tokens already enforce this.
  • QA matrix every phase: 375 / 414 / 768 / 1024 / 1440, plus an axe pass per primary screen.

09 Delivery plan

Seven phases. The order is a real dependency chain — the recurrence engine and UI primitives in Phase 2 unblock everything after it. Sizes are indicative for one experienced full-stack engineer.

Foundations

S · ~1 wk

An empty app that deploys, connects to the database, and refuses cross-boundary imports.

  • Scaffold Nx (pnpm); generate web + web-e2e, the seven feature-* libs as standalone projects, and ui, domain, config, updates, testing, db, auth.
  • Tailwind + design tokens ported from the mockups; fonts via next/font. Base primitives: Button, Input, Select, Dialog, Sheet, Tabs, Toast, Chip, Progress, Card, plus the responsive AppShell and SVG icon registry.
  • Module-boundary lint rules; shared tsconfig; Vitest + Playwright wired.
  • Provision Vercel project, Supabase (marketplace integration), Vercel KV, Blob store; Zod env schema.
  • CI: nx affected lint/test/build + Nx Cloud. Drizzle client factory + drizzle.config.ts + first migration (users).

Exit Preview + production deploy green; a smoke query hits Postgres; an intentional bad import fails lint.

Authentication

M · ~1–1.5 wk

Self-owned email + password with signup, login, verification, and reset.

  • Auth.js v5 Credentials + JWT; users, password_reset_tokens, email_verification_tokens; argon2id.
  • Screens: /signup, /login, /forgot-password, /reset-password/[token], minimal /account — mobile-first.
  • Zod server actions; KV rate limiting; Resend + React Email templates; HIBP breached-password check.
  • Middleware guard on (app); getCurrentUser() helper consumed by all later features.

Exit signup → verify → login → logout and forgot → reset → login pass end-to-end; expired/used tokens rejected.

Payments, tags & methods

L · ~2 wk

The Calendar screen, fully functional — the core of the product.

  • Tables tags, payment_methods, payments, payment_tags, payment_events; RLS policies + repository layer.
  • Recurrence engine in libs/domain: expand a payment into occurrences over a window (monthly / quarterly / annual, day-of-month, end conditions, timezone). Heavily unit-tested before any UI.
  • Methods CRUD with the customisable icon + colour picker; tags CRUD.
  • Payments create/edit (one-time + recurring), method + multi-tag; List view (grouped by date) + Calendar view + toggle; mark-occurrence-paid.

Exit Calendar screen works on phone and desktop; occurrences render correctly across a DST boundary.

Subscriptions & installments

M · ~1.5–2 wk

Two recurring-payment variants with their own screens.

  • Subscriptions: subscription_details (renewal date, started-on, reminder); list + monthly/yearly summary + renewal countdown; edit form.
  • Installments: installment_plans + installment_payments; schedule computation for both bases (end-date vs total-amount → derive count / final date); screen with progress bars, mark-period-paid, and the two-way "finish when" toggle.
  • A "money-out" aggregator in libs/domain (payments + installments + subscription occurrences) feeds the calendar and heatmap — so no feature-* lib ever imports another.

Exit Subscriptions and Installments screens match the mockups; editing a plan preserves already-paid periods.

Checklist & year heatmap

M · ~1.5 wk

The monthly manual-transfer to-do list and the year view.

  • manual_transfer_checklists + manual_transfer_items; generate from payments paid by manual transfer; "Regenerate" merges the schedule in while keeping manual edits and ticks; inline edit; month selector.
  • Heatmap aggregation across payments + installments; the calendar-cell component + monthly totals bars; "Year" added to the view toggle.

Exit Checklist and Heatmap screens functional; Regenerate never drops a completed item.

Debts & settlements

S–M · ~1 wk

Track money owed both directions, with partial and full settlement.

  • debts + debt_settlements; net-position summary; per-debt remaining balance and progress bar.
  • Record settlement (partial / full), settle-in-full shortcut, direction filters, settled state.

Exit Debts screen matches the mockup; balances and net position reconcile against the settlement log.

Update flow, files & hardening

M · ~1.5 wk

Ship 1.0.

  • /api/version + build-ID injection + useUpdateCheck + menu item + passive toast + reload; enable Vercel Skew Protection.
  • Vercel Blob: avatar upload + receipt attachments on payments and settlements.
  • Responsive + a11y + performance pass; empty and error states; optimistic updates; Sentry + Analytics.

Exit "Check for updates" reloads onto a fresh deploy; axe clean on every primary screen; Lighthouse mobile ≥ 90.

Indicative timeline

~10–12 weeks solo to a polished 1.0. ~6–8 weeks with two engineers — Phases 2–5 parallelise across the domain libs once the recurrence engine and UI primitives exist. Phases 0–1 are on the critical path and don't split.

11 Risks

  • Auth.js v5 is pre-stable. Pin the exact version, keep every call behind libs/auth, and budget one upgrade pass before 1.0.
  • Recurrence / occurrence modelling is the deepest logic in the app. Build and test the engine in Phase 2 before any screen consumes it. Compute-on-read is the chosen approach; revisit materialisation only if the heatmap query gets slow.
  • Supabase transaction pooler vs. Drizzle. prepare: false on the runtime connection; migrations only through the non-pooling URL; never migrate inside next build.
  • Timezone & DST on day-of-month math. Store due dates as date, not timestamptz; do all arithmetic in users.timezone; add explicit fixture tests around March/November.
  • Nx library over-fragmentation. One feature-<name> project per domain and no more. Split a feature into feature- / data-access- / ui- siblings only when it visibly outgrows a single barrel.
  • Reset-email deliverability. Dev runs on Resend's onboarding@resend.dev sandbox (owner-only delivery). A verified sending domain (SPF + DKIM) is required before preview/prod and before any non-owner tester can receive mail; monitor bounces once live.
  • Vercel × Nx build drift. Commit vercel.json and pin Node + Nx versions; keep the build command explicit rather than relying on auto-detection.
